# ADR-0009：标签词表的 CRUD 放在宿主，改名即合并、删除清引用

- 状态：已采纳（v0.3.2）
- 日期：2026-11-12
- 相关：PRD §7.7、US33、§11 M1.4；ADR-0003；PRD §5（标签规则语义）

## 背景

到 v0.3.1 为止，"标签定义"（`tagDefs`）只是**写入时的副产品**：`POST /tags` 里遇到没见过的词就 `ensureTagDef(name, 'manual')`，除此之外没有任何管理手段——不能新建空词、不能改名、不能删掉写错的词；写错一个错别字，它就会永远留在筛选下拉与右键子菜单里，并且身上挂着的那批会话也一起被绑死。

用户要求「要有一个标签管理界面」。真正要决定的是三件事：

1. 词表 CRUD 在客户端做还是宿主做？
2. 改名撞上已存在的词怎么办？
3. 删除一个词，跟着它的会话标签和规则怎么办？

## 决策

1. **CRUD 全部落在宿主（`host/tags.js` + `/tag-defs` 路由），客户端只发意图**：词表是持久化的用户数据，和规则、备注、会话标签在同一个 `state.json` 里。只有宿主能保证"改词表 + 改所有会话 + 改所有规则"是一个原子批次、一次落盘（`persistNow`）。客户端各自拼一份副本会立刻分叉：两个标签页同时改名就互相覆盖。
2. **改名即合并（merge-on-rename）**：目标名已存在时不报错、不产生两个同名词，而是把源词的所有引用改写成目标词，并保留**旧的** `createdAt`（词存在得更早），`source` 取目标词的原值。理由：用户改名的真实意图通常是"这个词写错了/想统一叫法"，报错只会让人手动一个个挪。
3. **删除清引用，但不动会话**：删词时清掉所有会话的 `tags` 与 `suggestedTags` 里该词（大小写不敏感），并清掉所有规则 `action.tags` 里的该词；若某条规则因此变空，**连规则一起删**——否则它会变成"命中但一个标签都不打"的空转规则，比删掉更难理解。会话本体（标题、备注、消息）一律不动。
4. **接受写入时清同名建议（v0.3.2 的第二个修复）**：`apply` 与 `renameDef` 都用 `withoutAccepted` 把"刚刚成为真标签"的同名建议从 `suggestedTags` 里剔除。此前 `op:'replace'` 只改 `tags`，于是行里出现"实心 chip + 虚化 chip"两个同名词。
5. **词表改动回灌面板用广播桥**：`POST /tag-defs` 成功 → 对话框 adopt 新词表 + `onChanged()` 刷新面板；任何标签写入 → `notifyTagWrite(ids)`（清 `metaCache`、重置词表缓存、重新探针、触发合并刷新）。原生子菜单这类"不经过 React"的入口因此也能让面板在一秒多内跟上。

## 后果

- `vocabulary()` 每次都要扫全部会话来算用量（约 190 条量级，实测可忽略）；随会话数增长，这是第一个该加缓存的地方。
- 合并式改名是有损的：两个词的创建时间与来源只剩一个，历史"这个词是什么时候由谁引入的"丢失。可接受——词表不是审计日志。
- 删除规则是**隐式副作用**，所以 `removeDef` 的返回值里带 `rules` 计数，界面二次确认里明确写"会从 N 个会话和引用它的规则上移除"。
- 词表 CRUD 走独立路由而不是复用 `POST /tags`：后者的语义是"给这些会话打这些标签"，混进"改词表"会让一个接口承担两种权限与两种失败模式。
- 没有做：标签颜色、排序自定义、别名/同义词、批量合并多个词（一次一个），以及"撤销"。都留给 M2。
